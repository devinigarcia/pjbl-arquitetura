Parte I — ARC42 · 1. Introdução e objetivos

1.1 Visão geral

O Conecta Store é um sistema de retaguarda para uma loja pequena: cadastro de produtos, controle de estoque por movimentações e registro de pedidos de clientes, com um painel que resume a operação. O domínio é simples de propósito. O objetivo do projeto não é o negócio em si, e sim demonstrar uma arquitetura distribuída completa funcionando na nuvem: microfrontend, API Gateway, BFF, dois microserviços com bancos diferentes e uma Azure Function, ligados por chamadas síncronas e por eventos.

Escolhemos produtos e pedidos porque os dois domínios precisam um do outro de um jeito que justifica cada peça: o pedido depende do preço e do estoque do produto (o que dá trabalho de verdade ao BFF) e a venda precisa baixar o estoque (o que dá um motivo real para usar eventos em vez de uma chamada direta entre microserviços).

Regras de negócio que valem destacar

  • Produto: SKU único, em maiúsculas; preço maior que zero; estoque nunca negativo; "estoque baixo" quando ≤ 5.
  • Estoque: não é editável. Só muda por movimentação de ENTRADA ou SAÍDA, que fica no histórico com o saldo resultante.
  • Pedido: de 1 a 20 itens, sem produto repetido, quantidade de 1 a 999; total calculado no servidor.
  • Status: PENDENTE → PAGO ou CANCELADO; PAGO → ENVIADO ou CANCELADO; ENVIADO → ENTREGUE. ENTREGUE e CANCELADO são finais.
  • Edição: dados do cliente só mudam com o pedido PENDENTE; itens nunca mudam.
  • Exclusão: só pedido CANCELADO pode ser excluído.
  • Criação pelo BFF: nome e preço vêm do catálogo; estoque insuficiente bloqueia o pedido (409) dizendo quanto foi pedido e quanto há.

6.3 O que acontece quando algo falha

SituaçãoComportamento
ms-produtos (ou ms-pedidos) fora do ar durante o /aggregated-dataResposta 200 com partial: true, o bloco daquela fonte como null e o motivo em sources. O painel mostra o aviso e o restante dos dados.
Function fora do arProdutos e pedidos aparecem normalmente; os indicadores ficam indisponíveis.
Microserviço fora do ar numa operação de CRUDBFF responde 502 UPSTREAM_UNAVAILABLE (504 em timeout), no formato padrão de erro.
Fila indisponível na hora de publicarO pedido já está gravado. O evento fica PENDENTE/FALHOU no outbox e o relay tenta de novo. GET /events mostra a situação.
ms-produtos fora do ar quando a Function processa o eventoA Function relança o erro; a fila reentrega até 5 vezes e depois move para a fila poison.
Mesma mensagem entregue duas vezesms-produtos reconhece o eventId e responde 200 duplicate: true, sem mexer no saldo.
Dois cancelamentos simultâneos do mesmo pedidoAtualização condicional (WHERE Status = @esperado): só um vence; o outro recebe 409. Sai um único evento de devolução.
Banco SQL gratuito "dormindo"O ms-pedidos tenta de novo por alguns segundos; se não der, responde 503 com Retry-After e o front tenta outra vez.

8. Conceitos transversais

8.1 Clean Architecture e Vertical Slice, garantidas por teste

As dependências sempre apontam para dentro: API → Application → Domain e Infrastructure → Application → Domain. API e Infrastructure não se conhecem; quem liga as duas é o main.ts. Dentro de Application e API, o código é organizado por funcionalidade, e uma funcionalidade não importa outra.

Para isso não depender de disciplina, cada projeto tem testes de arquitetura próprios: um pequeno scanner lê os import de todos os arquivos e verifica as regras abaixo. Se alguém quebrar uma delas, a esteira falha.

Regra verificadaExemplo de violação que o teste pega
Domain não importa nenhuma outra camada nem pacotesimport express from 'express' em domain/
Application só depende do Domain (pacotes: só zod)caso de uso importando o repositório SQL concreto
API não importa Infrastructure, e vice-versaendpoint lendo infrastructure/config
Driver de banco, SDK de fila e fetch só na Infrastructuremongodb ou mssql importado num handler
Uma feature não importa outraCreateOrder importando GetOrder
Toda feature tem <Feature>Handler e <Feature>Endpointpasta de feature sem adaptador HTTP

Os próprios testes plantam violações em arquivos fictícios e conferem que cada regra reclama — assim sabemos que um "passou" não é falso positivo. No front, o teste equivalente garante que os remotes não importam um do outro e que nenhuma tela usa fetch direto.

8.2 Event-driven: outbox, fila e idempotência

  • Transactional Outbox. O ms-pedidos grava o pedido e o evento (tabela OutboxMessages) na mesma transação. Ou os dois existem, ou nenhum.
  • Relay. Um componente do ms-pedidos lê os eventos pendentes e publica na fila. Ele é acionado logo depois do commit e só continua tentando enquanto houver evento pendente — não fica consultando o banco à toa, o que manteria o SQL gratuito acordado e gastaria a cota do mês.
  • Entrega pelo menos uma vez. Uma mensagem pode chegar repetida; nunca se perde.
  • Consumidor idempotente. Cada movimentação leva eventId = "<id do evento>:<id do produto>". O ms-produtos tem índice único nesse campo.
  • Contrato documentado. AsyncAPI 2.6 servido pelo ms-pedidos em /events/docs.
  • Consistência eventual assumida. O estoque baixa alguns segundos depois do pedido. A resposta do BFF já avisa (stock.mode: "event-driven") e o painel se atualiza sozinho.

8.3 Segurança

CamadaControle
BordaSubscription key obrigatória no gateway; limite de 120 chamadas/minuto por chave; CORS; HTTPS em tudo.
Gateway → BFFCabeçalho x-gateway-secret (Named Value secreto do APIM). O BFF compara em tempo constante e recusa quem não tem.

Limitação conhecida: a subscription key vai dentro do JavaScript do front, então qualquer pessoa consegue vê-la. Ela identifica a aplicação e sustenta o limite de uso, mas não substitui login de usuário — que ficou fora do escopo (ver seção 11).

8.4 Observabilidade

  • Correlation-id. Toda requisição recebe um x-correlation-id (ou reaproveita o que veio). Ele segue do front ao BFF, aos microserviços, à Function e dentro do próprio evento.
  • Logs estruturados em JSON (pino), com o correlation-id em cada linha.
  • Server-Timing. O /aggregated-data informa o tempo de cada fonte, visível na aba Network do navegador e no painel "Chamadas ao BFF" do front.
  • Health checks. /health em todos os serviços; o do BFF mostra a situação de cada dependência.
  • Eventos visíveis. GET /events lista o outbox com status PUBLICADO, PENDENTE ou FALHOU.

9. Decisões arquiteturais

ADR-01 — TypeScript e Node.js em todos os projetos

Contexto: o enunciado pede Node no BFF e deixa os demais livres. Decisão: uma linguagem só, do front à Function. Consequências: mesma estrutura, mesmas ferramentas de teste e o mesmo scanner de arquitetura em todos os repositórios; qualquer pessoa da equipe mexe em qualquer serviço. Abrimos mão de mostrar outra plataforma (.NET, por exemplo).

ADR-02 — Transactional Outbox para publicar eventos

Contexto: gravar no banco e publicar na fila são duas operações; se uma falhar, pedido e estoque divergem. Decisão: gravar o evento numa tabela na mesma transação do pedido e publicar depois, por um relay. Consequências: nenhum evento se perde; em troca, a entrega pode se repetir, o que exige consumidor idempotente (ADR-03).

ADR-03 — Idempotência no ms-produtos, com índice único

Contexto: a fila entrega pelo menos uma vez. Decisão: cada movimentação leva um eventId e o MongoDB tem índice único parcial nesse campo. Consequências: a garantia fica no banco, então vale até com duas instâncias processando ao mesmo tempo. A baixa usa $inc condicional (stock ≥ quantidade), sem precisar de transação.

ADR-04 — Azure Storage Queue em vez de Service Bus

Contexto: precisávamos de mensageria gratuita. Decisão: Storage Queue, que usa a conta de armazenamento que a Function já exige. Consequências: custo praticamente zero e gatilho nativo. Não tem tópicos nem ordenação garantida, o que não faz falta com um único consumidor; se surgirem mais consumidores, o ponto de troca é só a classe publicadora.

ADR-05 — Azure API Management em vez de AWS API Gateway

Contexto: o enunciado cita o gateway da AWS como opção. Decisão: APIM na camada Consumption. Consequências: uma nuvem só, uma conta só (sem cartão) e as rotas importadas do OpenAPI do BFF. A definição equivalente para AWS está versionada em gateway/aws/, caso se queira trocar.

ADR-06 — Azure Container Apps para BFF e microserviços

Contexto: o enunciado exige imagens no Docker Hub. Decisão: Container Apps puxando as imagens públicas. Consequências: HTTPS e URL pública prontos, escala até zero (sem custo parado). A primeira chamada depois de um tempo ocioso demora alguns segundos.

ADR-07 — Microfrontend com Module Federation num site só

Contexto: "microfrontend" precisa ser mais que uma SPA comum. Decisão: shell + dois remotes carregados em tempo de execução, publicados como um único site estático. Consequências: cada remote tem build próprio e também abre sozinho; se um falhar, o resto continua. Em contrapartida, os remotes precisam de build para rodar localmente.

ADR-08 — Validação de estoque no BFF, baixa por evento

Contexto: o pedido não deveria ser aceito sem estoque, mas a baixa é assíncrona. Decisão: o BFF confere o estoque antes de criar o pedido; a baixa real acontece pelo evento. Consequências: boa experiência no caso comum. Dois pedidos simultâneos do último item podem ser aceitos; o segundo evento recebe 409 do ms-produtos e fica registrado como alerta (ver risco R2).

11. Riscos e dívidas técnicas

#Risco / dívidaImpactoO que fizemos ou faríamos
R1Cold start: containers em escala zero e SQL gratuito pausado deixam a primeira chamada lentaMédioTimeout de 30 s no BFF, novas tentativas no ms-pedidos e no front. No dia da apresentação, subir com -MinReplicas 1 e "aquecer" antes.
R2Dois pedidos simultâneos do último item podem ser aceitos (a baixa é assíncrona)BaixoO estoque não fica negativo: o segundo evento é recusado e registrado. Evolução: reserva de estoque ou saga de compensação que cancela o pedido.
R3Não há autenticação de usuário; a chave do gateway é visível no frontMédioAceitável para o escopo. Evolução: login com Entra ID / OAuth e validação de JWT no gateway.
R4Cota mensal do SQL gratuitoBaixoRelay sem consulta periódica; painel pausa a atualização automática com a aba oculta; banco em AutoPause (nunca cobra).
R5/aggregated-data traz no máximo 100 produtos e 100 pedidosBaixoSuficiente para a demonstração. Evolução: indicadores calculados no banco ou por projeção alimentada pelos eventos.
R6Relay do outbox roda dentro do ms-pedidos (uma réplica)BaixoLimitamos a 1 réplica. Evolução: bloqueio de linha (READPAST) ou relay separado.
R7Excluir um produto não verifica pedidos antigos que o citamBaixoO pedido guarda nome e preço da época, então continua íntegro. Evolução: inativar em vez de excluir.
R8Mensagens na fila poison não têm tratamento automáticoBaixoFicam guardadas para análise manual. Evolução: alerta e tela de reprocessamento.

12. Glossário

TermoSignificado no projeto
BFFBackend for Frontend: API feita sob medida para a interface, que junta e adapta os dados dos microserviços.
MicrofrontendInterface dividida em partes com build e publicação independentes, montadas no navegador.
Shell / remoteNo Module Federation, o shell é a aplicação que hospeda; os remotes são as partes carregadas por ela.
API GatewayPonto único de entrada das APIs: autentica, limita e roteia.
Clean ArchitectureOrganização em camadas em que as regras de negócio não dependem de framework, banco ou interface.
Vertical SliceOrganização do código por funcionalidade (uma pasta por caso de uso), e não por tipo de arquivo.
Porta / adaptadorPorta é a interface que a aplicação define; adaptador é a implementação concreta (MongoDB, SQL, HTTP).
Composition rootLugar único onde as implementações são criadas e ligadas (main.ts).
Transactional OutboxPadrão que grava o evento no mesmo banco e transação do dado de negócio, para publicar depois com segurança.
RelayComponente que lê o outbox e publica os eventos na fila.
IdempotênciaRepetir a mesma operação não muda o resultado além da primeira vez.
Consistência eventualOs dados de serviços diferentes ficam coerentes depois de um curto intervalo, não no mesmo instante.
Correlation-idIdentificador que acompanha uma requisição por todos os serviços, para juntar os logs.
Subscription keyChave que o API Management exige em cada chamada.
Fila poisonFila para onde vão as mensagens que falharam em todas as tentativas.
AsyncAPIEspecificação para documentar eventos e mensagens, equivalente ao OpenAPI das APIs HTTP.
SKUCódigo único do produto.

Parte III — Canvas do projeto

Objetivo

  • Construir e publicar uma aplicação distribuída completa (microfrontend, gateway, BFF, dois microserviços, Function) para gestão de produtos e pedidos.
  • Aplicar Clean Architecture, Vertical Slice e arquitetura orientada a eventos, com evidência por testes.

Justificativa

  • Praticar, num caso pequeno e real, os padrões vistos na disciplina.
  • Produtos × pedidos obriga a integrar dois domínios, o que justifica BFF e eventos.

Partes interessadas

  • Professor (avaliador)
  • Equipe do projeto
  • Operador da loja (usuário)

Requisitos

  • CRUD de produtos e de pedidos
  • GET /aggregated-data
  • Eventos de pedido
  • Swagger em tudo
  • Gateway na entrada
  • Testes unitários e de arquitetura

Entregas

  • 6 repositórios públicos
  • 3 imagens no Docker Hub
  • Aplicação na nuvem
  • PDF (ARC42, C4, Canvas, prints)
  • Vídeo no YouTube

Premissas

  • Contas gratuitas disponíveis (Azure for Students, Atlas, GitHub, Docker Hub)
  • Volume baixo de dados
  • Um único tipo de usuário

Restrições

  • Custo zero
  • BFF em Node.js
  • MongoDB Atlas e Azure SQL gratuitos
  • Demonstração só com URLs públicas

  • Cota das camadas gratuitas

Solução (arquitetura)

  • React + Module Federation → Azure API Management → BFF (Express) → ms-produtos (MongoDB Atlas), ms-pedidos (Azure SQL) e Azure Function.
  • Outbox → Storage Queue → Function → estoque, com idempotência.
  • TypeScript em tudo; GitHub Actions; Container Apps.
